# TASK-UI-4 · Smart restaurant card

**Goal.** Cravera feels like an assistant helping you search, not a search-and-display app: each pick arrives as a detailed card that tells you what the place is and serves, with Cravera's own take on how it fits your craving, backed by Google Places data, and a full page (like Yelp's) one tap away. The rules for the AI parts are in [ADR 0005](adr/0005-traceable-ai-summaries.md). Background and the maintainer's words: [the smart card plan](plans/v0.3-smart-card.md).

## Acceptance criteria

Tick a box only after checking it in the running app with real data. Never delete or reword a criterion. Propose any change to the maintainer instead.

- [x] Before `place-details` is first deployed, a daily quota on Place Details is set in Google Cloud (maintainer) and the deploy is recorded with it.
- [x] Details load by themselves for each place as it is shown (the first pick, and each place after No), with one automatic Places Details request per shown place through an Edge Function (key server-side; only Try again after a failure spends another; repeated taps and rebuilds share a request already on its way); a place the guest hasn't reached loads nothing; search makes no details call and keeps its 11 s budget.
- [x] Photo gallery: up to 5 Places photos, each fetched only as the guest swipes to it, each with its author attribution; a place with no photos shows the placeholder.
- [x] The card itself, without a tap, shows enough to rely on: Cravera's take, the checked "Why this pick" facts, Google's description and review summary when Places has them, and the key attributes (what it serves and how: for example takeout, dine-in, vegetarian, beer/wine).
- [x] "See full page" opens a closable page over the card, like a Yelp page: photos, description, all reported attributes, up to 5 reviews, website (menu) and Google Maps buttons. Closing it returns to the same card; No and Yes keep working.
- [x] Reviews: each with author name, photo, rating, relative time and a link (Google's attribution rules), shown whole, under a neutral heading, never as a reason for the pick.
- [x] Attributes from Places only; an attribute Places doesn't report is not shown. Menu: Places has no menu items, so the website and Google Maps buttons stand in; no dishes are listed from Google data.
- [x] "Why this pick": up to 3 checked facts. Gemini returns only references to Places field names from a fixed list (and, separately, review numbers to order the reviews). The function checks each in code (attribute `true`, rating present, price only when the guest asked for a price range and it lies inside it), ignores anything else, and shows the server's wording. If Gemini fails or nothing survives: today's Places-only reasons, with Budget-friendly only when the guest asked for a price range and the price is inside the original range (also after a relaxed retry; never with no requested range).
- [x] Cravera's take: a short note (at most 3 sentences, 280 characters) in Cravera's voice on how the place fits the craving and what it thinks of it, from only the craving and that place's Places fields and reviews; labelled as Cravera's AI take on Google data and reviews; dropped in code if it has any digit or number word, a currency sign or price word, a link, or anything about hours or being open (quantities appear only in the server's wording of checked fields); when Gemini fails or the note is dropped, a template take in the same voice and under the same rules (no numbers, prices or hours) from checked fields only.
- [ ] While searching, Cravera shows what it understood from the craving (from the search intent: for example "ramen · cozy · nearby") and what it is doing, so the search reads as Cravera working; no place facts appear before Places answers.
- [ ] Failure paths: details that fail or time out leave the card with its search facts, a "Couldn't load more about this place" message and Try again; a failed take falls back to the template; No and Yes keep working throughout.
- [ ] Function tests for the fact check (denial cases: a review number given as a reason, a true price outside the requested range, a price with no requested range (also for Budget-friendly), a relaxed retry judged against the original range, a review number not in the input, an attribute `false` or absent, a field name not on the list, free text next to a valid reference), the take's checks (a digit, a number word, a number copied from the craving or a review, a price written without a currency sign, a link, an hours claim, an over-long note, each dropped to the template; the rendered template itself has no digits, prices or open-status words), details request counts (rebuilds and rapid taps share one request; a timeout then Try again spends exactly one more), the fallbacks and input validation (place ID format, publishable-key check, no logging of the craving or place); `flutter analyze` and `flutter test` pass, with widget tests for the loaded, partial (no photos/reviews/take) and failed states, the full page, and the accessibility guidelines at 1x and 2x text.
- [ ] Checked in the app on Android and iPhone with real cravings: detailed card, take, gallery, full page, reviews; key scan of the built app finds no Google key.
