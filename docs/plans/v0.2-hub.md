# Plan: accounts, a Saved hub, Profile and Friends (v0.2.0)

Status: direction decided by the maintainer (2026-11-27); each task's criteria still need approval before work starts. Delete after the last task merges, once lasting decisions move to ADRs and PRODUCT.md.

## Why

The maintainer, after the v0.1 redesign: Profile has no account fields and its settings are cluttered; Saved should be "a central hub for places you've been to or want to go", layered and functional (a map of saved places, grouped by city, customizable); Friends "feels like a ghost town". Today nothing persists: closing the app forgets bookmarks, and there are no accounts.

## Decisions (maintainer, 2026-11-27)

1. **Accounts first.** Build Supabase sign-up/sign-in now (the planned v0.2.0), so Saved and Profile are real and follow the user to any phone. No device-only storage that gets thrown away later.
2. **A real Google map on Saved.** Google's terms allow Places content only on a Google map, so Saved uses the Google Maps SDK. Its key lives in the app, restricted to the app's bundle ID (iOS) and package name and signing certificate (Android), and allowed only the Maps SDKs. The Places and Gemini keys stay server-side. This narrows ADR 0003's "no Google key in the app" rule to the Maps SDK key only; a new ADR records it before the key is added.
3. **Friends: an inviting preview for now.** A designed page that shows what friends will do in Cravera (share picks, see where friends eat) with an invite link, never an empty list. Real friends come after accounts.

## Constraints that shape the design

- **What we may store from Google** (Places API policies, as understood 2026-11-27; confirm against the current terms when TASK-004 starts): place IDs may be stored indefinitely; coordinates may be cached for up to 30 days; other content (names, photos, ratings, hours) must not be stored, only fetched when shown. So a saved place row holds the **place ID**, the user's own data (status, notes, tags, visited date) and coordinates with a `refreshed_at` date. Names and facts come from a server-side Place Details call when the hub opens (cost to check, Essentials fields where possible).
- **City grouping** comes from the place's address components at fetch time, not stored text.
- **Deny by default:** every table has RLS so a user reads and writes only their own rows; denial-path tests prove it (AGENTS.md P1 list).
