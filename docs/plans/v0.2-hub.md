# Plan: accounts, a Saved hub, Profile and Friends (v0.2.0)

Status: direction decided by the maintainer (2026-11-27); each task's criteria still need approval before work starts. Delete after the last task merges, once lasting decisions move to ADRs and PRODUCT.md.

## Why

The maintainer, after the v0.1 redesign: Profile has no account fields and its settings are cluttered; Saved should be "a central hub for places you've been to or want to go", layered and functional (a map of saved places, grouped by city, customizable); Friends "feels like a ghost town". Today nothing persists: closing the app forgets bookmarks, and there are no accounts.

## Decisions (maintainer, 2026-11-27)

1. **Accounts first.** Build Supabase sign-up/sign-in now (the planned v0.2.0), so Saved and Profile are real and follow the user to any phone. No device-only storage that gets thrown away later.
2. **A real Google map on Saved.** Google's terms allow Places content only on a Google map, so Saved uses the Google Maps SDK. Its key lives in the app, restricted to the app's bundle ID (iOS) and package name and signing certificate (Android), and allowed only the Maps SDKs. The Places and Gemini keys stay server-side. This narrows ADR 0003's "no Google key in the app" rule to the Maps SDK key only; a new ADR records it before the key is added.
3. **Friends: an inviting preview for now.** A designed page that shows what friends will do in Cravera (share picks, see where friends eat) with an invite link, never an empty list. Real friends come after accounts.

## Constraints that shape the design

- **What we may store from Google** (Places API policies, as understood 2026-11-27; confirm against the current terms when TASK-004 starts): place IDs may be stored indefinitely; coordinates may be cached for up to 30 days; other content (names, photos, ratings, hours) must not be stored, only fetched when shown. So a saved place row holds the **place ID**, the user's own data (status, notes, tags, visited date) and coordinates with a `refreshed_at` date. Names and facts come from a server-side Place Details call when the hub opens (cost to check, Essentials fields where possible).
- **City grouping** comes from the place's address components at fetch time, not stored text.
- **Deny by default:** every table has RLS so a user reads and writes only their own rows; denial-path tests prove it (AGENTS.md P1 list).

## TASK-003 · Accounts (spec for approval)

**Goal.** A guest can create a real account, sign in on any phone and sign out; their profile lives in Supabase, readable and writable only by them. Today's sign-in is a demo that only keeps a display name on the device.

**Review level:** L3 (auth, access control, personal data, the first migration).

**Needs the maintainer before work starts** (WORKING-AGREEMENT: dependencies, credentials, deployments):

1. **New dependency `supabase_flutter`** (official client: Auth, session storage on the device, database calls). Recommendation: yes; it is the stack in ADR 0002.
2. **Sign-in method:** email + password only for v0.2.0 (recommended), or also magic link / Sign in with Apple and Google now.
3. **Email confirmation:** keep Supabase's default (confirm before first sign-in; recommended) or off while testing. Supabase's built-in mailer is rate-limited; a custom SMTP sender is a later decision.
4. **Migrations on the production project:** first `supabase/migrations/` file, applied with `supabase db push` (a deploy: yours to approve each time).
5. **Delete account:** a small Edge Function that deletes the caller's own auth user with the service role, run server-side (App Store rule for apps with accounts).

**Acceptance criteria** (tick only after checking in the running app):

- [ ] Sign up with email + password creates an account and a `profiles` row (display name); wrong or reused emails, short passwords and network errors show clear messages.
- [ ] Sign in, sign out, and staying signed in after the app restarts work on Android (emulator) and iOS (Simulator).
- [ ] `profiles` (id = `auth.users.id`, display name, home city, dietary preferences, default radius, timestamps) has RLS on, deny by default: a user selects and updates only their own row; insert only via the sign-up trigger; no delete from the client.
- [ ] Denial-path tests against a local Supabase: another user's row can't be read, updated or created; anonymous requests get nothing; a client-supplied `id` grants nothing.
- [ ] Guest mode still works without an account; a guest can upgrade to an account from Profile and the prompt no longer promises features that don't exist yet.
- [ ] Delete account removes the auth user and their profile (server-side, the caller's own account only), with a confirm step; tested including a denial path.
- [ ] Nothing secret on the device: the bundled `.env` still holds only the URL and publishable key; the APK scan stays clean.
- [ ] `flutter analyze`, `flutter test` and the function tests pass; auth screens pass the accessibility guideline tests.

**Out of scope:** saved places (TASK-004), Profile redesign beyond the account section (TASK-UI-3), social sign-in unless decision 2 says otherwise.
