# Plan: make Cravera feel like a concierge (v0.1.0)

Status: decided by the maintainer (2026-11-27), except the TASK-002 spec, which waits for approval. Delete after merge, once lasting decisions move to an ADR and PRODUCT.md.

## Why

The live data pipeline works (TASK-001), but the maintainer's test on the emulator showed the product doesn't feel intelligent yet:

1. **Plain-language cravings fail.** "I just finished at the gym, I want something healthy and high protein but not too expensive and quick, something fast food like Chipotle" → "Nothing open matched". The whole sentence is sent to Google as the search text; Gemini isn't wired (TASK-002).
2. **The result looks like a Google search result**: a card that doesn't fill the screen, with no sense of *why* this place was picked.
3. **No way to reprompt from a result.** You can only say No, or reach the refine box after 3 Nos or when results run out.
4. **The filter sheet is fake.** It discards its values (PRODUCT.md, Phase 2).
5. **Home feels cluttered**: logo orb, greeting, headline, subtitle, drifting cards, 3+ quick-pick chips, a composer with filter, mic ("coming soon") and send buttons, a location chip and a 4-tab nav bar. It doesn't read as "just talk to it".

### TASK-002 · Craving intelligence (spec for approval)

**Goal.** The app understands what the guest is asking for, not just the words, and picks the open place that fits best. Nothing is hardcoded: no keyword tables, no canned answers. Gemini reads the craving and the candidates; Google Places stays the only source of restaurant facts (AGENTS.md).

**How it works** (inside `places-search`, still one call from the app):

1. **Understand.** Gemini turns the craving (plus the previous intent when refining, and the local time of day) into a validated JSON intent: `textQuery` (short and Places-friendly, for example "healthy high protein bowls"), an optional `includedType` from an allowed list, `priceLevels`, a distance hint ("quick" means nearer, capped by the existing radius limits), `wants` (for example "high protein", "fast") and `avoids` (for example "seafood").
2. **Search.** Places Text Search (New) with that intent: always open now, inside the radius, restaurants only (unchanged guarantees).
3. **Curate.** Gemini ranks the candidates against the intent, using only what Places returned (types, rating, price, Google's editorial summary when available), and returns an ordered list of place IDs. IDs it didn't receive are dropped; missing ones are appended in Places order. It never writes restaurant facts.
4. **Explain.** The card's "why this pick" line combines the intent's `wants` that the place matches with Places facts. It is never free text about the restaurant from the model.

**Acceptance criteria (draft):**

- [ ] "I just finished at the gym, I want something healthy and high protein but not too expensive and quick, something fast food like Chipotle" returns a fitting open place near the test location (healthy fast casual, $–$$), checked on the emulator.
- [ ] Varied phrasings give sensible intents (for example "something warm for a rainy night", "cheap late-night tacos", "quiet date spot, not too pricey"), covered by recorded fixtures in tests and spot-checked live.
- [ ] Refining from a result changes the intent instead of restarting: "cheaper" lowers the price, "no seafood" avoids seafood places.
- [ ] Curation returns only place IDs from the Places answer; every field shown still comes from Places.
- [ ] If Gemini fails, times out or returns invalid JSON, search still works with the raw text and Places order (tested).
- [ ] Prompt-injection attempts in the craving can't change open-now, the radius cap, the data source or the output shape (tested).
- [ ] The Gemini key exists only in Supabase secrets; the built app contains no key (APK scan).
- [ ] `flutter analyze`, `flutter test` and the function tests pass, with tests for intent validation, curation validation and the fallback (network faked).

**Review level:** L3 (a new external AI integration fed with untrusted input).
**Cost:** two Gemini calls per search (understand, then curate) on a Flash-class model. Confirm the current model and its free tier when building. Places calls don't change.
**Out of scope:** reviews, embeddings, other data sources (see the vision below), voice.

### Where the intelligence goes next (vision, maintainer 2026-11-27)

Cravera only stands out if the AI really understands the request and curates, instead of returning generic results. After TASK-002, roughly in order of effort:

1. **Reasoning over reviews:** fetch reviews for the top candidates and let Gemini check claims ("high protein", "quiet", "good for groups") against what diners say. More Places data per search, so it needs a cost cap.
2. **Semantic search (RAG):** embed reviews and descriptions of places near the user, retrieve by meaning ("cozy", "hidden gem", "authentic Sichuan"), then curate. Needs a vector store (Supabase pgvector) and a caching and refresh policy that fits Google's terms.
3. **Niche discovery from social sources** (for example TikTok): specific, trending or hidden places. Blocked on data access and terms (already in PRODUCT.md's idea backlog).

### TASK-UI-2 · Concierge redesign (sketch)

- **Palette:** food-appropriate (the maintainer: purple doesn't fit). Present 3 options as mockups to choose from; colours stay only in `lib/core/app_colors.dart`.
- **Home:** one hero input with rotating example cravings as hints, a small location chip, send. Quick picks appear as suggestions under the input only while it's empty. No filter or mic buttons until they work.
- **Pick screen:** full-screen; photo hero; name, rating, price, distance, open-until; "why this pick" line; large Yes / No; "Tell me more…" input and refine chips always visible; "New craving" in the corner; nav bar hidden here.
- **Refine chips replace the filter sheet:** Cheaper / Closer / Different cuisine / Healthier / distance presets. Each one is a reprompt through TASK-002, so they actually work.
- **Google attribution (must-do):** every photo author credit (with avatar and link when given), a link to the original photo on Google Maps, and the official Google Maps logo with Google's sizing and contrast rules.
- **Skills to use while building:** `design:design-system` (tokens for the new palette and type), `design:ux-copy` (hints, "why this pick", errors), `design:accessibility-review` (before merge), `design:design-critique` (on the new screens).

## Decisions (maintainer, 2026-11-27)

1. **TASK-002 (Gemini) first**, then the redesign. The AI must really understand and curate, never give hardcoded responses (see the vision above).
2. **Photos stay free:** only the first pick of each search gets a photo, so No makes no Google request (done in PR #17).
3. **Redesign scope: all four.** Minimal home, full-screen pick, always-on reprompt with refine chips (replacing the fake filter sheet), and a new food palette chosen from 3 mockups.
4. **Google attribution polish moves into TASK-UI-2** (deferred from PR #17's round 4) and is part of the gate before any build leaves the maintainer.

- Hide the mic button until voice exists (recommended: yes, in TASK-UI-2).
