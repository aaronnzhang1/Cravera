# TASK-005 · Refine that really refines (v0.1.0 blocker)

Status: **spec for approval** (written 2026-11-27 at the maintainer's request, relayed from the Mac session). Blocks the v0.1.0 tag ([PRODUCT.md](../PRODUCT.md#releases)). Delete this file once TASK-005 merges and lasting decisions move to ADRs.

**Review level (proposed):** L3. It changes `places-search` (external AI integration fed with untrusted input) and needs a deploy.

## What the maintainer saw

iPhone 16e simulator (iOS 26.3.1), San Francisco, build of 6007468, 2026-11-27:

> "every time i click cheaper or refine it, it returns the same set of restaurants in the same exact order. that doesnt feel very intelligent to me, especially if i pressed no the first time."

So the v0.1.0 exit criterion "No/refine work" fails on iPhone. The Android check earlier the same day ("nice dinner" → Cheaper went from $$$ to $) passed only because Gemini's curation happened to reorder; TASK-002 criterion 3 was ticked on that and does not hold in general.

## Diagnosis (code read on `main` 340b5be)

- **A (confirmed): price never reaches Google.** `buildRequestBody` (`supabase/functions/places-search/logic.ts:147`) sends only `textQuery` with the restaurant type, open-now and the location rectangle. The intent's `priceLevels` only steer ranking, by design, so "Cheaper" sends nearly the same text and Google returns the same ~20 places.
- **B (confirmed): the app forgets the Nos.** `CravingSearch.refine` → `_run` resets `_index` and `_rejections` (`mobile/Cravera/lib/services/craving_search.dart:162`) and sends no shown or rejected place IDs, so places the guest said No to come back first.
- **C (unverified): the reorder can be invisible.** Curation runs only with Gemini's intent, more than one result and at least 1500 ms of budget left (`logic.ts:345`, `MIN_CURATE_MS`), and it sees only name, cuisine, price, rating and distance, too little to judge "no seafood". When it is skipped or fails, `priceFirst` (`logic.ts:378`) barely changes the order. Check the `places-search` logs ("understand … curate …") to see which path the maintainer's taps took.

## Proposed approach

1. The app keeps the IDs of places shown in this search session (across refines) and sends them with a refine; the server leaves them out of the answer.
2. When the intent has `priceLevels`, send them to Places Text Search; if that finds nothing open, retry once without the price filter (fits the existing budget; still open-now and inside the radius).
3. Give curation more Places facts per candidate (`primaryType`/`types`, `editorialSummary`, and `serves*` flags if fetched) so exclusions like "no seafood" can be applied. Gemini still returns only an order of the refs it was given; it never produces restaurant data.

## Acceptance criteria

Tick a box only after checking it in the running app. Never delete or reword a criterion. Propose any change to the maintainer instead.

- [ ] (a) Within one search session, a refine never shows a place the guest already said No to, neither first nor later.
- [ ] (b) "Cheaper" changes the Places request (`priceLevels` sent), with one relaxed retry without the price filter if that returns nothing open.
- [ ] (c) The curate step receives enough Places facts to apply exclusions like "no seafood", and still returns only refs it was sent.
- [ ] (d) Tests: a refine never returns a rejected place (app and function); "cheaper" changes the request body; the relaxed retry; IDs from the app are validated (untrusted input, capped in number).
- [ ] (e) v0.1.0 criterion "No/refine work" re-checked by hand on the Android emulator and the iPhone simulator.
